# 일기 API 100초 요청 예산 — 2026-11-09

`/api/diary`의 생성·검토·재작성·재검토가 공유하는 전체 요청 예산을 100초로 제한한다. BE의 기존 135초 제한과 FE 제한, 모델 선택·키·Render 설정은 변경하지 않는다.

## 처리 방식

- 요청 시작 시 단조 시계(monotonic)로 하나의 deadline을 만든다. 응답 구성에 1초를 남겨 모델 작업은 99초 이내의 예산으로 수행한다. 스레드 큐에서 기다린 시간도 예산에 포함한다.
- 각 호출 직전에 남은 시간을 다시 계산한다. SDK timeout은 남은 예산과 60초 중 작은 값이다. 생성·재작성에는 남은 예산의 절반까지만 배정하여 뒤의 검토 시간을 남긴다. 공유 클라이언트의 기본 timeout은 변경하지 않는다. SDK 재시도는 계속 0회다.
- 최초 검토 거절 후 모델 예산이 10초 미만이면 재작성·재검토를 생략한다. 10초 이상이면 한 번만 시도하며 두 호출 모두 동일한 deadline을 사용한다. 10초는 성공 보장이 아닌 최소 시도 예산이다.
- 호출 전후에 deadline을 확인하여 늦게 도착한 후보·승인을 사용하지 않고, 다음 모델 호출도 시작하지 않는다.
- HTTP 경로에는 별도 AnyIO 벽시계 제한을 둔다. 모델 예산보다 0.5초 더 기다리는 최대 99.5초 후, 아직 끝나지 않은 작업의 대기를 중단하고 원문 fallback을 구성한다. SDK timeout은 HTTP 연결/읽기 등 단계별 timeout이므로 이것만으로 전체 요청을 제한하지 않는다.

HTTP 제한은 기다리는 시간을 중단하는 장치다. 파이썬 스레드 및 공급자에서 이미 진행 중인 호출을 강제 종료하거나 비용을 취소한다고 보장하지 않는다. 완료가 늦어지면 결과는 폐기하고 추가 검토·재작성은 수행하지 않는다. 네트워크 전송과 OS 스케줄링 자체의 절대 지연까지 보장하는 실시간 시스템은 아니다. 서비스는 100초 중 응답 여유 시간을 두어 BE 135초 제한을 늘리지 않고 응답하도록 구성했다.

## 결과와 오류 구분

| 상황 | 결과 |
| --- | --- |
| 출처 검증 및 검토 통과, 예산 이내 | 기존 `fallback=false` 일기 |
| 검토 거절, 충분한 시간 | 한 번 재작성·재검토 |
| 검토 거절, 재작성 시간 부족 | 원문 `fallback=true` |
| 최종 거절·잘못된 출처·잘못된 문장 수/길이 | 기존 원문 `fallback=true` |
| 전체 예산 소진·HTTP 벽시계 제한 | 원문 `fallback=true`, 미검토 후보는 반환하지 않음 |
| 실제 공급자 오류·개별 SDK timeout·모델 응답 형식 오류 | 기존 HTTP 오류(ProviderRouter 변환 오류는 503), 재시도 없음 |

원문 fallback과 정상 응답의 JSON 계약은 그대로다. `sources`는 원래 child 인덱스·원문 전체를 보존하고, `pages`는 최대 6개, `imageUrl=null`, `requires_confirmation=true`를 유지한다. mock에서도 공급자를 호출하지 않는다.

기존 고정 진단 로그에 `budget_exhausted`, `repair_skipped_budget`, `request_budget_exhausted`를 추가한다. 생성/검토 공급자 실패는 기존 `generation_failed`/`review_failed`, 검토 거절은 `review_rejected`로 구분한다. 로그에는 단계·시도 번호만 기록하며 아이 원문·후보·키·공급자 원본 오류는 넣지 않는다.

## 검증

`tests/test_diary_budget.py`에서 실제 API 대신 가짜 시계·Provider와 SDK MockTransport를 사용했다.

- 느린 정상 생성·검토와 4회 호출이 하나의 예산을 공유하는지 검증.
- 잔여 시간이 10초 미만일 때 재작성 생략, 정확히 10초일 때 제한된 시도 검증.
- 생성·검토·재작성·재검토에서 늦게 도착한 결과를 폐기하고 추가 호출을 하지 않는지 검증.
- 이미 끝난 예산에서는 모델을 전혀 호출하지 않는지 검증.
- timeout 인자를 무시하고 블로킹하는 가짜 Provider를 사용해, HTTP 응답이 먼저 fallback으로 끝나는지 짧은 실제 시간 예산으로 검증.
- Groq/OpenAI SDK의 모의 읽기 timeout이 재시도 없는 503으로 구분되고, 전달 timeout과 공유 클라이언트 설정·로그 비노출이 유지되는지 검증.
- 기존 회귀 테스트로 요청·응답 JSON, 출처·정정·짧은 답변·안전한 fallback 검증 유지.

실행 결과: `.venv/bin/python -m pytest tests/test_diary_budget.py -q` 15개 통과, `.venv/bin/python -m pytest -q` 전체 147개 통과, `git diff --check` 통과.

실제 Groq 호출·유료 작업·Render 배포는 수행하지 않는다. main 반영은 사용자 요청에 따른 커밋·푸시로만 수행한다.
